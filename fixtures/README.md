# Fixtures

This directory holds the compatibility corpus and reference material for
differential testing against the reference implementation (the existing
MusicPack repository's C library and CLI).

## What is committed

### `reference/` — manifest fixtures (unmodified copies)

| File | Provenance | Used for |
|------|-----------|----------|
| `*.mpack-manifest.json` | the *originally committed* fixture manifests from the reference packages (`tests/reference/`); Python-generated, alphabetically sorted keys | parsing/semantic tests — note these are **not** canonical-writer output (discrepancy D6 in `docs/architecture.md`) |
| `canonical-*.json` | manifests rewritten by the reference CLI's `update-metadata` (which serializes through the C canonical writer, including unknown-root-field preservation) | **byte-identity tests** for the Rust canonical writer |
| `mpak-source/` | a tiny directory bundle (manifest + three small members) authored for container testing | input for the MPAK compatibility tests |
| `reference-small.mpak` | `musicpack pack fixtures/reference/mpak-source` output from the reference CLI | **byte-identity tests** for the Rust MPAK writer; reference-reader tests |

The canonical/container files were produced with the reference tooling on
copies; the reference fixtures themselves were never touched. Regeneration
instructions are in the headers of `tests/manifest_write.rs` and
`tests/mpak_compat.rs`.

### `reference/audio/` — audio fixtures (unmodified copies)

The reference repository's committed `tests/fixtures/audio/` set, copied
byte-for-byte (provenance: `core/libmusicpack` / `tests/audio_tests.c`):

| File | Content | Used for |
|------|---------|----------|
| `flac16-44k.flac`, `flac-mono-44k.flac` | 16-bit FLAC, 44.1 kHz, 88 200 frames | FLAC format/frame parity, reference PCM digests |
| `flac24-48k.flac`, `flac24-96k.flac` | 24-bit FLAC, 48/96 kHz | FLAC parity + the 24-bit `s32`↔`f32` consistency check |
| `flac-long-48k.flac` | 16-bit mono, 30 min silent stress fixture | format-only smoke test (full decode is too slow for the unit suite) |
| `wav16-44k.wav`, `wav24-44k.wav` | native PCM WAV | WAV format/frame parity and conversions |
| `wav24-ext.wav` | `WAVE_FORMAT_EXTENSIBLE` PCM 24-bit | the non-canonical GUID quirk (discrepancy **D11**) |
| `wav-float.wav` | 32-bit IEEE-float WAV | raw-bit passthrough; `s32` rejection |
| `wav-adpcm.wav` | ADPCM (tag 2) | explicit rejection |
| `wav-truncated.wav` | declared 88 200 frames, physically short | truncated-data semantics |

`tests/data/audio_c_reference.txt` holds the reference PCM digests: the
SHA-256 of each fixture's interleaved left-aligned `s32` and `f32` streams
as decoded by the reference's **vendored `dr_flac`** through
`tools/audio_probe.c` (build/regeneration command in that file's header).
The Rust `claxon`-backed adapter must reproduce the `s32` bytes exactly and
the `f32` bytes per the shared `2^-(bits-1)` rule.

### `tests/data/analysis_c_reference.txt` — Phase 9 analysis goldens

Compact deterministic records produced by `tools/analysis_probe.c`, which
compiles the reference's `waveform.c`, `loudness.c` and vendored ebur128
1.2.6 (build/regeneration command in that file's header; the probe is
Unix-only because ebur128 needs `sys/queue.h`, but CI consumes only the
committed table):

- `waveform <label> points=<n> sha256=<hex> head=<8B> tail=<4B>` —
  **byte-exact** golden for the `peak-rms-u8` payload; `tests/analysis.rs`
  reconstructs the same PCM (committed FLAC fixtures via the Phase 8
  decoder, or the probe's bit-reproducible synthetic generator) and compares.
- `loudness <label> lufs=<%.17g> tp=<%.17g>` — integrated loudness and true
  peak, compared within ±0.05 LU / ±0.05 dBTP.

Synthetic cases use only operations reproducible bit-for-bit in C and Rust
(integer LCG, power-of-two scaling) plus silence/DC/impulse, so no generated
binaries are committed.

### `tests/data/player_oracle.jsonl` — Phase 10 player-core oracle

Deterministic JSONL emitted by `tools/player_oracle.ts`, which imports the
reference TypeScript `web/player-core` package directly and records the
Sweet-Fade planner, gain policy, session snapshot codec, deterministic queue
operations and 15 scripted player scenarios (driven through a fake engine).
`tests/player_oracle.rs` replays every record against the Rust port and
compares the observable result. Regenerate by bundling the tool with the
reference checkout's `esbuild` and running the bundle under Node (exact
command in the tool header); the committed file is what CI consumes.

### `tests/data/g8_c_reference.txt` — `%.8g` number vectors

3394 `<hex f64 bits> <canonical output>` pairs generated by running the
real C `snprintf` calls of the reference's `json_number` (`tools/g8_probe.c`
contains the program and the regeneration command). These are the
empirical proof of the Rust `%.8g` port. Values in the UB region
(integral doubles beyond ±9.2e18, where the C branch decision is
undefined) are excluded — see discrepancy D2.

## The conformance corpus

The authoritative corpus (72 cases: 6 valid / 57 invalid-manifest /
9 invalid-verify) is **generated at test time**, not committed — exactly
as in the reference repository:

- `tests/support/mod.rs` is a byte-exact Rust port of the reference
  generator (`generate_mpack_conformance.py`); `tests/conformance_corpus.rs`
  byte-compares the port's output against the Python generator when a
  reference checkout + `python3` are available, and asserts the
  authoritative parse + verification outcome for every case.
- `tests/conformance_differential.rs` runs the same corpus through the
  reference CLI's `info` and `verify` and the Rust verifier, comparing
  accept/reject decisions (currently zero divergences).

The deterministic **fuzz-lite corpus** (`tests/fuzz_lite.rs`) reuses the
committed `test-musicpack-album.mpack-manifest.json` as its base: it
truncates it at every 97th byte, applies the reference's 30 seeded
bit-flip mutations (reproduced byte-for-byte via a CPython-compatible
MT19937 port) and seven path injections — no additional fixtures.

### Reference-repository discovery

No absolute paths are baked in. Resolution order (differential layers
skip with a printed notice when unavailable):

1. `MUSICPACK_REFERENCE_DIR` — the reference repository checkout;
   falls back to the sibling `../musicpack`.
2. `MUSICPACK_REF_CLI` — the reference `musicpack` CLI binary; falls
   back to `<reference>/build/core/musicpack/musicpack`. Build it once
   with the cmake invocation documented in the differential test header.

**The harness never modifies or regenerates the reference fixtures.**
Corpus materialisation happens in per-process temporary directories; the
reference checkout is only ever read (and its own generator writes only
to the temp dir).

## Known gaps

None in the format/verification/container scope:

- all 72 conformance cases pass parse plus full verification, and the
  differential run against the reference CLI matches on `info` and
  `verify` with zero gaps;
- MPAK packs are byte-identical to reference CLI packs, and the reference
  CLI verifies and unpacks Rust containers (`tests/mpak_differential.rs`).

Remaining documented items are qualitative, not corpus gaps: sonic
document validation, a Windows directory adapter, remote/OPFS byte
sources, and the CLI-level `unpack` surface (see `docs/architecture.md`
Open Questions O11/O12/O14/O15).
