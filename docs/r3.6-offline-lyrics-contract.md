# R3.6 — Offline lyrics contract (design investigation)

> **Status: investigation complete; decisions resolved and implemented in
> R3.6** (see the resolution block below). This document remains the
> evidence record for the contract; the normative rules now live in
> `docs/musicpack-lyrics-v1.md` §7.4 and §11.

> **R3.6 resolution (implementation).** All §12 questions are decided:
> (1) delivery = the release-level index (no N+1, no planner resolver);
> (2) field = top-level `trackLyrics`, entries
> `{trackId, id, url, size, sha256, lang?}`, omitted when empty, appended
> after `assets`; (3) `sha256` is mandatory in that index — hashless rows
> never enter it and the planner never hashes to compensate;
> (4) lyrics are **non-critical** on integrity failure (install commits,
> document recorded damaged and excluded from availability — the
> alternate-representation class; the installer's critical set is now an
> explicit allowlist of primary audio, waveforms and artwork);
> (5) offline key = `t.<trackId>.lyr.<assetId>`; (6) root-level lyrics
> stay deferred; (7) `checkForUpdate` derives lyric hashes from the same
> index (required for correctness once lyrics are staged); (8)
> availability gains one narrow lookup (`lyricKeyFor(trackId, assetId)`)
> so a damaged document can never be offered. Implementation sites:
> server `store/read.rs` (shared lyric read) + `http/routes.rs` (index
> member); web `api/types.ts`, `offline/{plan,types,installer,availability,manager}.ts`;
> tests in `crates/musicpack-server/tests/lyrics_server.rs`,
> `web/tests/unit/offline/*`, `web/tests/e2e/specs/offline.spec.ts`.

## 1. Status

The lyrics vertical is complete end to end and green:

```text
Author (R3.5) → .lrc → track.lyrics[] → .mpack
   → server ingestion (R3.3) → track detail lyrics[]
   → GET /api/v1/assets/{id} → core lyrics parser → Web LyricsPanel (R3.4)
```

Offline lyrics were deliberately deferred twice: R3.4 stopped at the
documented planner boundary (`web/app/src/lib/offline/plan.ts`, comment
block) and R3.5 stopped at the same boundary. The unresolved question is
only *how the planner learns the complete set of a release's track-lyric
references*: N+1 `GET /tracks/{id}` calls, or an additive release-level
index.

## 2. Current offline planner architecture

Traced from `web/app/src/lib/offline/` and ADR 0008.

```text
release payload (ReleaseDetail)
   ↓  planReleaseAssets()          (pure function, no fetch, no storage)
PlannedAsset[]                     (deterministic key + url + size + sha256?)
   ↓  Installer.run()              (sequential per-asset staging)
stage → hash-while-streaming → size check → verify
   ↓  fileStore.commit(installId, keys)      (staging → committed namespace)
   ↓  catalog.putPackage(record)             (ONE atomic publish point)
InstalledPackage { releaseDetail snapshot, assets[], bytes, … }
   ↓
availability.findAsset/localKeyFor  → playback source `{kind:'local-file', url:key}`
```

Facts that matter here:

- **`planReleaseAssets` is pure** (`web/app/src/lib/offline/plan.ts:23`,
  `plan.ts:34`): it takes a structural subset of `ReleaseDetail` and
  performs no I/O. Its determinism is a stated design property
  ("Pure function over ReleaseDetail: Node-testable, no fetch, no
  storage").
- **Asset identity is key-based, not index-based** (`plan.ts:27`):
  `t.<trackId>.primary`, `t.<trackId>.r.<representationId>`,
  `t.<trackId>.w`, `art.<artworkId>`. Keys are the OPFS file names and the
  offline lookup identity.
- **`PlannedAsset`** (`offline/types.ts:34`) carries
  `{key, kind, trackId?, representationId?, artworkId?, url, size, sha256?}`.
  `sha256` and `size` are optional by type; the planner skips assets with
  no usable size (`plan.ts:56`) and artwork enters with `size: 0`
  ("artwork size is not declared by the API; staged then measured",
  `plan.ts:97`).
- **Installer verification** (`offline/installer.ts:197`): bytes are read
  in chunks, SHA-256 is computed incrementally **only when the plan
  declares one** (`installer.ts:211`), size is compared when declared
  (`installer.ts:232`), hash mismatch is a hard `INTEGRITY` error
  (`installer.ts:235`).
- **Criticality policy** (`installer.ts:27`): `isCritical(asset) =
  asset.kind !== 'audio-representation'`. A critical integrity failure
  fails the whole install; a non-critical one commits the package with
  the asset marked damaged and excluded from availability
  (`installer.ts:142`).
- **Commit is atomic** by catalog record (`offline/stores.ts:46`);
  `InstalledPackage` persists the full `releaseDetail` snapshot
  (`offline/types.ts:67`) and per-asset records.
- **Availability is audio-only** (`offline/availability.ts:58`):
  `findAsset` matches `audio-primary` / `audio-representation` by track
  (and representation id). There is no lookup path for any other kind
  yet.
- **Boot audit is size-only** (`offline/audit.ts:32`): missing file →
  damaged; present file → size compared when declared. Hashes are not
  re-verified at boot.
- **Staleness check** (`offline/manager.ts:243`): `collectHashes(release)`
  derives expected hashes from the *release payload* for primaries and
  representations only — waveforms and artwork are already outside the
  update check today.
- **Offline byte access** goes through `FileStore.read(key)` /
  `readStream(key)` (`offline/stores.ts:29`); playback passes the key as
  the source URL (`state/queue.ts:80`).

## 3. Current lyrics API/data flow

Server contracts (R3.3, `docs/musicpack-lyrics-v1.md` §7):

- `GET /api/v1/tracks/{id}` ends with `"context":{…},"lyrics":[…]`; the
  field is **omitted** when the track has no lyric documents, and each
  entry is `{id, url, size, mimeType, sha256?, lang?}` (`§7.3`).
- `GET /api/v1/releases/{id}` `assets[]` lists **package-level assets
  only** (`assets.track_id IS NULL`); `media[].tracks[]` are unchanged
  track objects with **no** `lyrics` field. Both were verified live in
  this investigation (§13).
- Bytes are served by the existing `GET|HEAD /api/v1/assets/{id}`
  (strong sha256 ETag, Range, `text/plain` from the frozen extension
  table). No lyrics-specific endpoint exists by design.

Measured live (a 4-track `.mpack`, one package; `/api/v1` responses,
authenticated, byte counts include headers-free bodies):

| response | bytes |
|---|---|
| `GET /releases/1` | 3,657 |
| `GET /tracks/1..4` | 641 / 634 / 639 / 642 |
| `GET /tracks/5` (same track shape **with one lyric ref**) | 799 |
| one lyric ref, compact JSON | 168 |

So a single lyric reference costs ≈ **+160 bytes** in a track-detail
body, and the release payload (`3.6 KB` for 4 tracks) does not carry any
lyrics information.

Release `assets[]` entries are
`{id, kind, mimeType, sha256, url}` — note **no `size`**, unlike
track-detail lyric refs and unlike audio objects. Artwork entries are the
same shape.

## 4. Offline lyric requirements

Derived from the planner + installer + offline-serving path, not from the
DTOs:

**Required for staging (the planner/installer contract)**

| item | why |
|---|---|
| track id | offline lookup identity and key component, exactly like `t.<id>.primary` |
| lyric asset id | stable identity (R3.3 ids are stable across rescans and update in place on content change); key component; URL derivation |
| URL | the installer fetches it (`installer.ts:203`) |
| SHA-256 | the only integrity guarantee; verified incrementally (`installer.ts:211–237`) |
| byte size | progress accounting, storage total, staging/audit size check (`audit.ts:44`) |

**Required for offline *serving* parity (not for staging)**

| item | why |
|---|---|
| stable ordering | spec §5: "first entry in manifest order" is the selection rule; the offline copy must present the same order as online |
| optional `lang` | the LyricsPanel shows the tag; offline must render what online renders |

**Not required by the offline contract**

- package-relative asset paths (server-internal; never exposed by the API)
- file names / MIME type *as trust inputs* (MIME is display metadata; the
  panel does not branch on it today)
- lyric **contents** (bytes are fetched through the asset endpoint, never
  embedded in any index)
- root/package-level `lyrics[]` (no consuming feature; deferred since R3.4)
- language preference/ranking, waveform-like derived fields, `kind`
  (implied by the collection it lives in)

## 5. Waveform analogy

Waveforms are the closest existing per-track auxiliary asset, and they
already ride the release payload:

```text
manifest waveform ref
  → server track_waveforms row
  → release media[].tracks[].waveform {version,intervalMs,encoding,floorDb,points,sha256,url}
  → planReleaseAssets: key `t.<trackId>.w`, size = points * 2
  → installer hash/size verification
  → offline seek control reads FileStore by key
```

Reusable for lyrics, verbatim:

- the `PlannedAsset` shape and the identity-keyed naming convention;
- the fetch → incremental-hash → size-check → staged → atomic-commit
  pipeline;
- the offline read seam (`FileStore.read(key)`), which is agnostic to
  what the bytes mean;
- the existing `Manager.checkForUpdate` pattern (compare online hash vs
  committed record, flag only).

**Not** reusable, and why the analogy stops:

1. **Where the reference comes from.** The waveform ref lives *inside*
   the release track object; the lyric ref lives *only* on track detail
   by R3.3 decision (`§7.3`). The waveform analogy therefore does not by
   itself justify copying the waveform *placement*; it justifies the
   *staging machinery*.
2. **Cardinality and ordering.** One waveform per track; lyrics are an
   ordered array (0..n) whose **first entry is semantically selected**
   (spec §5). A lyrics key must be asset-id-based; the `t.<trackId>.w`
   single-asset pattern cannot be copied literally. The spec's
   approximate `t.<trackId>.lyr.<n>` (`§11`) must not be read as an array
   index — an index would re-key assets when the array is reordered,
   while the server's asset ids are stable. This is flagged in §12.
3. **Criticality.** Waveforms are currently *critical*
   (`isCritical = kind !== 'audio-representation'`), yet `§11` of the
   lyrics spec describes a failed lyric hash as behaving "exactly like a
   damaged waveform (non-critical asset…)". The two statements disagree;
   see §12.
4. **Update detection.** `collectHashes` covers audio + representations
   only; a lyrics addition would need its own hash source (which depends
   on the chosen reference mechanism).

## 6. N+1 analysis

What it concretely means with the current code:

```text
GET /api/v1/releases/{id}          (existing)
GET /api/v1/tracks/{t1}            ← for lyrics
GET /api/v1/tracks/{t2}
…
GET /api/v1/tracks/{tN}
```

- **Request count:** N additional GETs for an N-track release (measured
  bodies ≈ 640–800 bytes each; §3). Requests are independent and could
  be issued in parallel; the `ApiClient` has no batch helper today, so
  the caller would loop (a small `Promise.all` fan-out would be trivial
  in the client, but nothing existing does it).
- **Planner purity:** the planner cannot fetch. Either the manager
  pre-fetches details and assembles a widened input object for
  `planReleaseAssets`, or the planner grows a data-resolver port. Both
  change a documented, unit-tested design property ("pure; no fetch, no
  storage"), though neither breaks determinism *if* the fetched refs are
  passed in as data.
- **Offline serving:** the refs must survive into the committed package
  record. The installer currently persists `releaseDetail` verbatim; with
  N+1 the record needs a **new client-side field** for the per-track
  lyric refs (or the manager must merge them into a synthesized snapshot,
  which no longer matches the server payload). Without that, offline
  lyrics cannot know which assets it holds.
- **Caching:** HTTP caching does not help — track detail is
  `private, max-age=0, must-revalidate` for the *asset* endpoint, and
  track detail responses are ordinary authenticated JSON; each install
  re-fetches N details unless the app adds its own cache. The R3.4 track
  page already fetched *one* detail (the visible track) on demand, so
  browsing cost is unchanged; install cost is the new N requests.
- **Determinism:** preserved (refs arrive as data; keys are
  identity-based).
- **Lyric-less tracks:** their detail responses simply omit `lyrics`
  (200, no field) — no special-casing, but note a 404 is impossible to
  distinguish from "no lyrics" by shape alone; the client must treat
  absence as "nothing to plan".
- **Multiple lyric files per track:** all entries arrive in one detail
  response, in order — the planner can key each by asset id.
- **Language metadata:** available per ref, same as today.
- **Track vanishes between release and detail:** `GET /tracks/{id}`
  returns 404 (the release response had listed the track). The install
  needs an explicit policy: fail, or continue with partial lyrics. No
  such policy exists today because nothing is fetched mid-install.
- **Reference changes during planning:** each fetch returns its own
  snapshot; a lyric hash fetched later than the audio hashes can make the
  installed set *mixed-vintage*. Every asset is still verified against
  its own declared hash (no silent corruption), but the package no longer
  corresponds to one server-consistent view.
- **Partial/network failure:** a failed detail fetch turns an otherwise
  complete audio install into a decision point (abort vs. degrade). This
  is new failure surface the installer does not have today.

## 7. Release-level index analysis

The smallest additive representation that lets the planner stage all
track lyrics without N+1 is a **single release-level array of lyric
references**, each carrying its owning track id. Three shapes were
considered against the existing DTO conventions:

| shape | verdict |
|---|---|
| extend `assets[]` with a `trackId` on track-linked rows | **rejected** — the R3.3 contract (task §11 / spec §7.3) explicitly requires `assets[]` to stay package-level only so existing clients never see track-linked rows |
| add `lyrics[]` to each `media[].tracks[]` object in the release response | possible/additive, but it changes every track object in list responses and duplicates the track-detail field shape; contradicts §7.3's explicit "track list responses are unchanged" note |
| **a new top-level array** (e.g. `trackLyrics`) of the same ref shape plus `trackId` | **smallest**: no existing object changes, omitted entirely when the release has no track lyrics |

Properties of the third shape (all verified in code):

- **Payload size:** ≈ 180 bytes per reference (measured ref 168 bytes +
  `trackId` field). A 12-track album with one document per track adds a
  labelled *estimate* of ≈ 2.2 KB on top of a release payload measured at
  3.6 KB for 4 tracks (≈ 8–9 KB extrapolated for 12 tracks). Lyrics are
  small text files; the reference index is negligible next to audio.
- **Request count:** unchanged (1 release GET).
- **Determinism:** the server orders by `track_id, id`; asset ids are
  stable (R3.3) and content changes update in place, keeping keys stable.
- **Cacheability:** the whole index rides the release payload that the
  app already caches/stores.
- **Server query complexity:** one additional read over `assets`
  (`WHERE release_id = ?1 AND kind = 'lyrics' AND track_id IS NOT NULL
  ORDER BY track_id, id`), served by the existing `assets_release_idx`;
  mirrors the existing `track_lyrics` read. One `Store` method + one JSON
  member appended to the release object.
- **SQL/migration:** **none** — the v11 columns already exist. Pre-v11
  databases have no track-linked rows, so the array is omitted and
  responses are byte-identical.
- **Duplication:** the index would repeat what track detail returns.
  That is the deliberate cost of avoiding N+1; it is the same kind of
  duplication the release payload already accepts for audio/artwork
  objects (track detail re-serves them too).
- **Backward compatibility:** purely additive; ADR 0007 permits additive
  v1 fields and the C oracle compares bodies byte-for-byte, so the field
  must be **omitted when empty** on lyric-less fixtures (the same rule
  that kept R3.3's track field oracle-safe). A lyrics-bearing package
  needs the documented C-boundary treatment already used in
  `tests/lyrics_server.rs` (Rust body = C body + appended member).
- **Package-level lyrics:** excluded by `track_id IS NOT NULL`; root
  lyrics never leak into the track-level collection.
- **Language:** optional per reference, exactly as today.

## 8. Consistency analysis

Neither mechanism provides transactionality: the server holds no lock
across a release response and later track-detail requests, and the
installer's real guarantee is per-asset hash verification at download
time.

```text
N+1:      release @T0 ──► detail(t1) @T1 ──► … ──► detail(tN) @TN
index:    release (audio hashes + lyric hashes + refs) @T0
```

- With N+1, the installed **audio** set and the installed **lyrics** set
  can come from different library states (T0 vs T1…TN). Each hash still
  matches its own declaration, so no corruption is possible, but the
  snapshot is mixed-vintage.
- With the release index, all hashes and refs come from one response —
  a narrower window, no stronger guarantee.
- A mid-plan content change either way surfaces as an integrity failure
  at download time (critical → install fails; non-critical → damaged),
  or not at all if the planner never sees the new hash.
- The existing staleness check (`checkForUpdate`) already has this
  property for waveforms/artwork (not compared today); lyrics would
  inherit whichever mechanism supplies the refs to `collectHashes`.

There is **no evidence** that either approach needs (or should claim) a
stronger consistency boundary than the current per-asset verification.

## 9. Security/trust analysis

Existing trust boundary, end to end:

```text
package manifest track.lyrics[].sha256      ← authoritative (author/R3.5, verified at ingest)
   ↓ server ingests, stores assets.sha256(, file_size, lang)
GET /tracks/{id} (or a release index)       ← the client's ONLY source of expected hashes
   ↓ client fetches GET /api/v1/assets/{id}
client computes SHA-256 while streaming     ← verification, never a trust source
mismatch → INTEGRITY → criticality policy
```

- Expected hashes originate in the package and are served, never
  client-derived. Lyric staging can reuse this boundary **exactly**: no
  new key material, no new endpoint, no client-side trust decision.
- Filenames, `lang`, `mimeType`, and paths must never be treated as
  integrity inputs; the server already resolves assets by id, not path.
- The off-by-default plan shape (`sha256?`) means a plan *could* omit
  hashes; lyrics should not rely on that — every lyric ref carries a
  hash upstream, so the planner should propagate it.
- Known existing limitation to inherit consciously: the boot audit
  checks **sizes**, not hashes (`audit.ts`), so post-install bit rot is
  detected only on re-install. This is unchanged by either option.

## 10. Neutral comparison table

| Dimension | N+1 track details | Release-level lyrics index |
|---|---|---|
| Additional requests | N per release install (N = track count; measured ≈ 640–800 B each) | 0 |
| Payload size | release 3.6 KB (4-track, measured) + N details ≈ 3–10 KB | release + ≈ 180 B/ref (≈ +2.2 KB estimate for 12 tracks, labelled) |
| Implementation complexity | client prefetch loop + widened planner input + handling 404/partial failure | one server read + one JSON member + planner branch |
| Server complexity | none | one `Store` method, one query (existing index), C-boundary doc/tests |
| Client complexity | planner purity contract changes; committed record needs a new field to serve offline | planner consumes a field that already travels in the payload it is given; record snapshot already persists it |
| Cacheability | per-detail responses are not cached by the app; each install re-fetches | index rides the payload the app already keeps |
| Consistency boundary | release @T0 vs details @T1…TN (mixed-vintage) | one response snapshot (narrower, not transactional) |
| Backward compatibility | fully additive, no server or DTO change | additive field; must be omitted-when-empty to keep C byte-parity; needs the documented C-boundary test for lyrics-bearing fixtures |
| Multiple lyric files | all in one detail response, ordered | all in one index, ordered |
| Language metadata | present | present |
| Failure handling | new failure surface (detail fetch 404/network mid-install) with no policy today | rides the existing single-request failure path |
| Determinism | preserved (refs as data) | preserved (server-ordered, id-keyed) |
| Future extensibility | any future per-track metadata needs another round trip | one index can grow fields additively (e.g. root lyrics, credits) |

Where the repository does not settle a cell: the N+1 request par-
allelism/backoff policy and the release-index field *name/shape* are not
established anywhere; both are open (§12). No end-to-end latency
measurement was made — the comparison is request-shape and size based
(measured where noted), not a benchmark.

## 11. Minimum offline lyrics contract

Derived from §2/§4; independent of which delivery mechanism is chosen.
One record per lyric document, carrying:

```text
trackId     number   owning track (offline lookup identity)
id          number   lyric asset id (stable per R3.3; key + endpoint identity)
url         string   existing /api/v1/assets/{id} (fetch source at install)
sha256      string   package-authoritative hash (verification; never optional here)
size        number   byte count (progress, staging check, audit, storage total)
lang?       string   optional language tag (offline render parity)
```

Plus two protocol rules:

1. **Ordering:** the array must be in the server's deterministic order
   (per track: asset id order = first-inserted manifest order, R3.3);
   selection stays "first entry wins" (spec §5), so offline and online
   select identically.
2. **Key:** the offline key must be identity-based —
   `t.<trackId>.lyr.<assetId>` — never an array index, so reordering or
   adding documents never re-keys or collides.

Explicitly **not** part of the contract:

- package-relative paths, manifest file names, package fingerprints;
- lyric text/bytes (fetched, never indexed);
- MIME type as a trust input (display only; may ride along for parity but
  the planner must not depend on it);
- root/package-level lyrics (no consumer);
- language preference/ranking, default-language heuristics;
- derived/analysis fields of any kind.

## 12. Open decisions

**All six were resolved in the R3.6 implementation slice — see the
resolution block at the top of this document for the decisions; this
section is kept as the record of what was open and why.**

1. **Delivery mechanism** (the subject of this document): N+1 vs
   release-level index. The evidence (§10) leans toward the release
   index — it preserves the planner's purity, avoids the new mid-install
   failure surface, gives offline serving a persisted ref source for
   free, and is additive/omitted-when-empty so the C oracle stays safe —
   but the repository also commits in §7.3 that release responses "keep
   their exact shape", so choosing it is an explicit **contract
   revision** that needs sign-off, not a silent change. Decision: **open**.
2. **Field name/shape** if the index is chosen: must follow the existing
   camelCase/omitted-when-empty conventions; not decided here.
3. **Lyrics criticality on integrity failure:** the spec says non-critical
   (`§11`), the installer's current rule makes waveforms — and any new
   kind — critical. This is a behaviour decision with test consequences;
   **open**.
4. **Asset key spelling:** the spec's `t.<trackId>.lyr.<n>` needs the
   `n` defined as the asset id (§11 above); the spec text is currently
   approximate. **Open** (documentation fix).
5. **Interim online behaviour:** whether the online `checkForUpdate`
   should compare lyric hashes once a mechanism exists; today it compares
   audio + representations only. **Open**.
6. **Root-level lyrics:** remain deferred (no consumer).

## 13. Recommended next implementation boundary

**Do not implement inside this phase.** When R3.6 is authorized, keep it
to one bounded slice whose only externally visible change is the delivery
mechanism that §12.1 settles:

1. **Decision first (small, explicit):** pick §12.1 and, if the release
   index is chosen, §12.2 + §12.4 in the same act; if N+1 is chosen,
   write down the partial-failure and staleness policies first (they do
   not exist today).
2. **Contract edits:** `docs/musicpack-lyrics-v1.md` §11 — replace the
   R3.4 deferral note with the chosen mechanism, the derived minimum
   contract (§11 of this document), the key spelling, and the decided
   criticality.
3. **Server slice (only if the index is chosen):** one `Store` read
   method + one query over the existing v11 columns, one appended JSON
   member on the release response (omitted when empty), and the C-oracle
   boundary test for a lyrics-bearing release (pattern already in
   `crates/musicpack-server/tests/lyrics_server.rs`). No migration, no
   new endpoint.
4. **Client slice:** extend `OfflineAssetKind`/`PlannedAsset` with
   `lyrics` (asset-id keyed) + `planReleaseAssets` branch + installer
   criticality per the decision + offline availability/lookup for the
   LyricsPanel read path (`FileStore.read(key)` when offline, asset
   endpoint when online). Planner stays pure either way; N+1 would put
   the detail prefetch in `manager.install`, not in the planner.
5. **Tests:** planner unit tests (keys/order/size/multiple refs/lang),
   installer criticality + integrity behaviour, `checkForUpdate`
   coverage per §12.5, and one e2e extension of `offline.spec.ts`
   (download → airplane → LyricsPanel renders from local bytes) — reusing
   the existing offline e2e harness rather than a new suite.

Everything outside this slice (now-playing lyrics, root-level lyrics UI,
language preference, sidecar swap) stays out of scope.

### Verification of this investigation

after measurement (no repository or fixture changes):

- `GET /api/v1/releases/{id}` → 3,657 / 3,648 bytes (4 tracks, with and

  799 bytes with one lyric ref appended after `context`; ref = 168 bytes.
- Confirmed release `media[].tracks[]` carry no `lyrics` field, and
  release `assets[]` entries carry no `size`.
- Confirmed `assets[]` stays package-level (`track_id IS NULL`), so the
  R3.3 separation holds.

with live C oracle 179/0; web unit 452 passed / 2 skipped; web offline
unit 36/36; `cargo fmt --all --check` clean.
