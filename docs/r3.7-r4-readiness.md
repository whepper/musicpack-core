# R3.7 — R4 readiness & legacy dependency audit

**Status: investigation only.** R3.7 changed no source, test, format, schema,
or the legacy repository. This document is the only artifact. It audits the
repository *as it currently stands* (after R3.6) and answers what R4 must
actually do; it supersedes the historical phase plan where the implementation
has overtaken it.

*Scope of evidence: the current working tree of `musicpack-core`. The sibling
`../musicpack` checkout is treated strictly as the immutable reference/oracle
and is not inspected as living code except where a differential harness points
at it.*

---

## 1. Executive summary

**The modern runtime still requires the legacy implementation in exactly two
places:**

1. **The Author desktop app** (`author/src-tauri`) spawns three frozen legacy
   C binaries for *all* package authoring — the `musicpack` CLI (inspect,
   validate-draft, identify-draft, build-draft, verify, pack), the `mpcenc`
   Musepack encoder, and the `musicpack-sonic` ONNX analyzer. R3.5 added a
   narrow Rust overlay (lyric attach + lyrics-bearing `.mpak` packing) but the
   package pipeline itself is still the C sidecar.
2. **The web player** still loads the frozen Emscripten Musepack decoder
   (`web/app/public/musepack.{js,wasm}`) for **offline/OPFS Musepack playback**
   and for the `?legacyPlayback=1` escape hatch. Network playback already
   defaults to the Rust/WASM engine.

**Everything else is already Rust-authoritative and oracle-pinned:** the
server (runtime-independent, no subprocess/FFI, opens C v10 databases), server
ingestion and identity, the HTTP API and byte serving, the database layer,
package reading and MPAK writing, manifest parsing/canonical writing,
verification, the Musepack SV8 decoder, FLAC/WAV decode, waveform/loudness
analysis, the player domain and PCM engine, representation policy, and the
entire lyrics vertical (R3.2–R3.6).

**R4 is therefore not a broad rewrite.** It is:
an Author-pipeline migration (with the package-directory builder and the
already-complete Rust encoder wired in), the retirement of the C sidecars from
the runtime, the completion of the server's cutover closure (ops +
retirement decision), and — if desired — moving web offline Musepack playback
onto the Rust engine so the frozen decoder becomes oracle-only.

Two things must **not** be "finished" by deletion: the LGPL-licensed
encoder/tools crates (a deliberate permanent licensing boundary) and the
compatibility/oracle infrastructure (corpora, generators, frozen fixtures,
differential suites). See §13.

## 3. Part II — Runtime dependency map

### A. Server startup
`server executable` → `cli.rs`/`main.rs` → `config.rs` → `store::SqliteStore::open`
→ embedded migrations (1–11, `store/schema.rs`) → startup `ingest::scan`
(unless `--no-scan`) → `http::serve`. **No legacy code at any point.** The only
C in-process is the bundled SQLite amalgamation inside `rusqlite`, explicitly
scoped by D-S2/O-S1 and isolated behind the `Store` trait
(`crates/musicpack-server/src/lib.rs:17` is `#![forbid(unsafe_code)]`).

### B. Server ingestion
`filesystem` → `discover.rs` (bounded walk, symlinks never followed) →
core `format::manifest` parse → core `validation::verify` → `identity.rs`
(fingerprint/group/release keys) → `ingest.rs` state machine → SQLite. All Rust.
The only "codec" step is a **header probe** (`probe.rs`): SV8 via the Rust
decoder, FLAC via a byte-exact STREAMINFO parse, extension fallback otherwise.
**SV7 takes the failed-probe path** (O-S3, not triggered by any fixture) — a
documented gap, not a C dependency.

### C. Server API
All endpoints are Rust (`http/routes.rs`): health, session lifecycle,
artists/albums/releases/tracks, `library/scan|verify|status`, and byte serving
(`tracks/{id}/audio|waveform`, `representations/{rid}/audio`, `assets/{id}`).
The legacy C server appears **only** in optional differential tests
(`MUSICPACK_LEGACY_SERVER`, skipped with a notice when unset). The Rust server
is fully authoritative for the API contract.

### D. Audio playback
`Web/player` → `controller.ts::chooseBackend`:
- network Musepack/FLAC/WAV → **Rust/WASM** (`rust-playback.worker.js` +
  `rust-playback-sink.js`, generated binding) — the default;
- browser-supported non-Musepack → native `<audio>`;
- **OPFS `local-file` Musepack → the frozen Emscripten decoder**
  (`musepack-engine.ts` → `decoder.worker.js` → `localreader.js`), and
  `?legacyPlayback=1` forces the legacy lane entirely.

So the network decode path never invokes a legacy decoder; **offline Musepack
playback does**. FLAC/WAV offline uses the native backend, not the frozen
decoder. The C `libmpcdec` is otherwise used only as a test oracle.

### E. Author package creation
`Author UI` → Tauri commands → `AuthorService` → **spawns the C `musicpack`
CLI** for `inspect`/`validate-draft`/`identify-draft`/`build-draft`/`verify`/
`pack`/`waveform-draft`/`encode-draft`, which internally spawns C `mpcenc`;
`musicpack-sonic` is spawned for sonic analysis. R3.5 post-processing is Rust:
after a C `build-draft`, `track_lyrics::attach_to_package` parses/mutates/writes
the manifest canonically and re-verifies with the core; a lyrics-bearing
`.mpak` is written by `format::mpak::write_mpak` instead of `musicpack pack`
(because the C packer would drop lyric files). **The `.mpack` directory itself
is always produced by C.**

### F. Offline installation
`release detail` → pure TS planner (`offline/plan.ts`, including the R3.6
`trackLyrics` index) → downloader → Rust-core integrity semantics
(sha256/size) → OPFS `FileStore` → IndexedDB catalog → availability. No legacy
code in planning/installing/verifying. The **playback** of the installed
Musepack files is the one legacy touchpoint (D above).

### G. Web / WASM classification
- **Rust/WASM-backed**: playback decode/engine for network sources, the
  representation resolver, and the lyrics parser/bindings (`lyrics-core.ts`).
- **TypeScript-only (not legacy)**: the Svelte app, router, API client, queue
  orchestration, offline planner/installer/catalog, waveform windowing,
  representation preference, session/media-session glue, `player-core` domain.
- **Legacy-backed**: the frozen Emscripten Musepack decoder (offline/escape).
- **Compatibility-only**: the `rust-differential`/`rust-soak`/`rust-observation`
  e2e specs and `tests/node/` decoder harness.

## 5. Part IV — Package writer audit

**Q1 — What the Rust/core writer already supports.**
Manifest parse + canonical write with unknown-root-field preservation
(`src/format/manifest/{parse,write}.rs`); path rules (`format::path`); SHA-256
(`format::checksum`); waveform envelope format (`format::waveform`);
deterministic MPAK v1 writer/reader, byte-identical to the reference
(`format::mpak::{read,write}`); full verification (`validation::verify` +
`storage` backends); WAV/FLAC/Musepack decode, waveform accumulator, BS.1770
loudness (`audio::*`). The Rust encoder reproduces `mpcenc` streams for all 21
whole-encoder cases.

**Q2 — What the C writer still provides (in the Author path).**
Everything between a tagged album and a package: source scanning, asset hashing,
embedded-artwork extraction, loudness measurement orchestration, metadata
reconciliation, `draft_to_manifest`, draft validation, MusicBrainz match/apply,
directory assembly (`build-draft`), encode orchestration (`encode-draft`),
waveform (`waveform-draft`), `verify`, and `pack` — invoked as
`Command::new(self.cli_path())` (`author_service.rs:237,308,376,434,506,1026`).

**Q3 — Features missing from Rust.**
There is **no `.mpack` directory builder in core** (the writable sibling of
`verify_directory` that ADR 0002 and architecture-review §11 name), **no draft
model / draft→manifest translation**, **no authoring CLI surface** (the Rust
`musicpack` CLI is `info|verify|pack|unpack` only, `crates/musicpack/src/cli.rs:25-31`),
and **no MusicBrainz match/apply** (the host does only the HTTP lookup:
`author/src-tauri/src/musicbrainz.rs`).

**Q4 — What must remain byte-compatible.** Canonical manifest bytes and MPAK v1
container bytes are permanent contracts (ADR 0007) and are already proven
byte-identical by Rust. Directory assembly is a *logical* layout; its
compatibility requirement is that the produced manifest, file bytes/hashes and
final `.mpak` match the reference — not that the C function is reused.

**Q5 — What only needs semantic compatibility.** Draft validation verdicts,
identify confidence, encode orchestration and waveform generation are
semantic/behavioural; their oracle is the frozen C CLI's JSON output and the
byte-exact analysis corpora.

**Q6 — Which package variants still require C.** *All of them today*, for the
directory build; the C `pack` is skipped only for lyrics-bearing `.mpak`
(`author_service.rs:694-699`), which uses the core MPAK writer.

**Q7 — What proves equivalence.** `tests/manifest_write.rs` (byte-identity),
`tests/mpak_compat.rs`/`mpak_differential.rs` (byte-identical packs, cross
verify/unpack), `crates/musicpack/tests/differential.rs` (CLI exit codes/bytes),
`tests/analysis.rs` + `tests/data/analysis_c_reference.txt` (waveform byte-exact,
loudness ±0.05), `tests/audio.rs` + `audio_c_reference.txt` (FLAC PCM), the
encoder's `encoder_whole` (21/21) and `reference_manifest`, and `cut_compat`
(12/12).

**Q8 — Smallest vertical slice for Rust authority.** Core `.mpack` directory
builder + a minimal draft→manifest path, exposed as the first authoring
subcommand and differentially compared to the C CLI on a committed fixture
album. That is the enabling slice; encode/waveform/identify follow.

**Q9 — What remains a compatibility oracle afterwards.** The frozen C CLI (and
its build tree) for differential JSON/byte comparisons; the frozen corpora and
manifest; the live `MUSICPACK_*` suites. None needs to be a runtime dependency.

**Q10 — Is there a fundamental reason C must remain?** No. The only genuine
capability gap is MusicBrainz **matching** (a library function in the C CLI);
the HTTP lookup already lives in Rust. Everything else is either already ported
or is assembly/orchestration. The current dependency is a migration gap, not an
architectural boundary.

## 6. Part V — Server cutover audit

**Runtime independence: yes.** No `Command`/`spawn`/FFI in production code; the
only C is bundled SQLite inside `rusqlite`, confined to the crate
(`crates/musicpack-server/Cargo.toml`, D-S2/O-S1).

- **Existing v11 databases / C-created v10 databases:** yes. A committed C v10
  fixture opens and migrates in place (`db_compat.rs:88-166`); the C opens a
  Rust v11 DB (its migration loop falls through on the higher version) and
  simply cannot see the new columns; Rust refuses `schema_version > 11` with
  `DatabaseTooNew` (`store/sqlite.rs:166-179`, `store/schema.rs:26`).
- **C↔Rust interoperation:** proven bidirectionally when the legacy binary is
  supplied (`db_compat.rs:296-365`).
- **All required endpoints:** implemented (see §3C); no stubs; unknown routes
  answer the documented 404s.
- **Authentication/session:** complete (bearer→cookie exchange, sliding session,
  revocation inheritance, `Secure` negotiation) and oracle-pinned.
- **Discovery/ingestion/verification/asset serving:** complete and
  oracle-pinned.
- **Any production path shelling out to C:** none.
- **C dependency kept only for oracle testing:** yes (the C server binary).

**What still prevents the Rust server from being the authoritative runtime?**
Nothing structural. The remaining items are:
1. **Deployment artifacts** — docker/compose and deployment docs (ADR 0009 /
   `docs/server-cutover-checklist.md` §8). *Documentation/ops, not code.*
2. **Graceful shutdown** — the C waits for a running job; the Rust server
   terminates directly (documented divergence, ADR 0009; safe by WAL
   atomicity). *Decision: implement signal handling or accept the divergence.*
3. **SV7 probe gap (O-S3)** — the C indexes `musepack-sv7`; the Rust core
   rejects SV7, so the probe falls through. *No fixture triggers it; a
   header-only SV7 parse would close it.*
4. **The explicit retirement decision** and cutover sign-off
   (`docs/server-cutover-checklist.md` §8), including the release-build
   differential run and the deployment-host smoke.

## 7. Part VI — Player / engine cutover audit

`audio input → decoder → PCM → engine → player → Web/UI`:

- **Rust-authoritative:** the player domain (`core::player`), the PCM engine
  (`musicpack-engine`), the host seam (`musicpack-host`), the WASM binding,
  representation policy, and **all decoders** (Musepack SV8, FLAC via `claxon`,
  WAV) for the network path.
- **Legacy during playback:** the frozen Emscripten Musepack decoder for OPFS
  `local-file` sources and the `?legacyPlayback=1` hatch. This is a real user
  path (any offline Musepack album).
- **Legacy for comparison only:** `libmpcdec` (WASM) in `tools/musepack_oracle.mjs`
  and the differential e2e specs.
- **TypeScript orchestrator:** `web/player-core` remains the web domain core
  (queue/transition/snapshot/gain), consumed by `controller.ts`; the Rust engine
  is the default backend. ADR 0003 explicitly leaves a single-implementation
  cutover unscheduled and evidence-gated.
- **Intentional:** seek is reopen+skip (D18); no device backend is wired (O17).

Musepack decoding is fully independent in Rust (byte-identical PCM) for online
playback; the offline web path is the only gap.

## 8. Part VII — Musepack encoder boundary

- `crates/musicpack-musepack-encoder/` is a **source-derived
  LGPL-2.1-or-later** implementation whose status is "migration complete —
  production `PCM→SV8` encoder", bit-exact for all 21 whole-encoder cases
  (`README.md:6-14`, `tests/encoder_whole.rs`). `musicpack-core` must never
  depend on it (one-way isolation; root `AGENTS.md`/`Cargo.toml`).
- `crates/musicpack-mpc-tools/` (also LGPL) provides the `mpccut`-equivalent
  container surgery (12/12 byte-identical) and deliberately omits `mpc2sv8`
  (needs SV7 decode, out of scope).
- **Neither crate has a runtime consumer today**: the Author encodes through the
  C `mpcenc` sidecar; nothing depends on either crate except `mpc-tools →
  encoder`.

Verdict: **(2) a permanent isolated licensing boundary, with an outstanding
integration task.** The boundary itself must stay; the `mpcenc` *sidecar* is
migration debt that the boundary's crate can retire. This is not "temporary
Rust scaffolding to delete" — it is the long-term licensed implementation.

## 9. Part VIII — Lyrics status

The vertical is complete and green through R3.6:

```text
Author (R3.5) → core parser/model (R3.2) → .mpack manifest track.lyrics[]
   → server ingestion + v11 (R3.3) → TrackDetail.lyrics[]
   → GET /api/v1/assets/{id} → online LyricsPanel (R3.4)
   → release.trackLyrics[] (R3.6) → offline planner → installer
   → offline availability lookup
```

Explicitly deferred, none of which blocks R4:
- offline lyrics **presentation UI** (no offline lyrics UI, no language
  selector, no now-playing surface);
- **root-level** `lyrics[]` (no consumer; D3);
- **now-playing** lyrics surface;
- **language preference/ranking**;
- **sidecar → core** lyric migration (no sidecar lyric model exists; the legacy
  root-level attachment remains the R3 Author scope and its per-track authoring
  is the R4 draft-model work — `docs/musicpack-lyrics-v1.md` §6.6, Q11).

The only intersection with R4 is that the **draft model gains `track.lyrics`
additively when the Rust authoring pipeline exists** (§5 Q3); that is R4.2 work,
not new R3 scope.

## 12. Part XI — Legacy repository boundary

- The legacy repo is **never modified** by this workspace: no build step, test,
  or script writes to `../musicpack`; the only scripts that invoke it are
  optional oracle/differential harnesses.
- It is **not required at runtime**: the Author sidecars are prebuilt frozen
  artifacts resolved from the app bundle (packaged) or local build trees/env
  vars (development); the web uses committed frozen artifacts.
- It is **required only** to regenerate oracles or run optional live
  differentials (via `MUSICPACK_REF_CLI`/`MUSICPACK_REFERENCE_DIR`,
  `MUSICPACK_LEGACY_SERVER`, `MUSICPACK_MPCENC`, `MUSICPACK_MPC_WASM_JS`).
- The modern repository operates fully without a local `../musicpack` checkout;
  CI proves this (it never checks it out).

## 13. Part XII — R4 candidate slices

Five slices. Each is the smallest unit that removes or reduces a real
dependency; ordering follows §15.

### R4.1 — Core package-directory builder + identity promotion

**Goal.** Make Rust able to write a canonical `.mpack` directory (and move
identity keys out of the server crate into core), unblocking every authoring
command.
**Current state.** Manifest/MPAK writers, verification, decode, waveform and
loudness all exist in core; identity exists in `crates/musicpack-server`.
**Remaining gap.** No directory assembler; no draft→manifest translation;
identity is server-private.
**Scope.** New core module (directory/package builder) + `identity` move with
its golden vectors; no behavior change to readers.
**Proof.** Differential vs C `build-draft` on a committed album; manifest
byte-identity; verify round-trip; existing identity vectors.
**Legacy after.** Oracle-only.
**Risk.** Reproducing metadata reconciliation/asset layout exactly.

### R4.2 — Rust authoring pipeline (`crates/musicpack-author` or CLI extension)

**Goal.** Provide the JSON command surface the Author consumes
(`inspect`/`validate-draft`/`encode-draft`/`waveform-draft`/`build-draft`/
`identify-draft`/`verify`/`pack`) implemented in Rust.
**Current state.** Core primitives + complete Rust encoder; Rust CLI covers
`info/verify/pack/unpack`; host does MB HTTP.
**Remaining gap.** Draft model, draft validation, encode orchestration,
waveform command, MusicBrainz **matching**, and the CLI contract.
**Scope.** New app-level crate; wire `musicpack-musepack-encoder`; keep the CLI
JSON shape so the UI barely changes (architecture-review §11).
**Proof.** Command-by-command differential vs the frozen C CLI; encoder
`encoder_whole`; analysis corpora; produced-package byte/verify parity.
**Legacy after.** Oracle-only.
**Risk.** MusicBrainz matching fidelity (the one no-Rust-equivalent capability)
and loudness/artwork semantics.

### R4.3 — Author cutover (retire the sidecars)

**Goal.** Re-point the Tauri app to the Rust pipeline; bundle no C `musicpack`
or `mpcenc`; keep behavior identical.
**Current state.** `author_service.rs` spawns frozen sidecars; `tauri.conf.json`
bundles them.
**Remaining gap.** R4.2; a decision on the sonic analyzer's fate.
**Scope.** `author_service.rs`, `tauri.conf.json`, packaging/CI, sidecar
removal; sonic stays host-side app logic.
**Proof.** Author unit/component suites, build smoke, byte parity of output
packages, backend-resolution tests rewritten to the Rust backend.
**Legacy after.** Removed from the runtime/bundle; frozen C CLI retained only as
a dev oracle.
**Risk.** Sonic analyzer has no Rust equivalent (may remain an intentional
app-level C/ONNX boundary — decide in this slice).

### R4.4 — Web offline playback on the Rust engine

**Goal.** Remove the frozen Emscripten decoder from the runtime path by giving
the Rust/WASM engine an OPFS byte source, so offline Musepack plays through
Rust.
**Current state.** Network decode is Rust; OPFS `local-file` routes to the
frozen decoder.
**Remaining gap.** A browser source adapter over
`FileSystemSyncAccessHandle`/OPFS, and `chooseBackend` routing.
**Scope.** Web worker/source adapter + controller selector; no domain change.
**Proof.** Offline e2e on the Rust backend; differential vs the legacy decoder
over committed fixtures; `rust-error-verify`.
**Legacy after.** Oracle-only (artifact optionally retained for provenance and
the rollback hatch).
**Risk.** Worker/OPFS/SharedArrayBuffer plumbing and offline performance.

### R4.5 — Server production cutover closure

**Goal.** Finish the server's stage-8/9 closure and record the retirement
decision.
**Current state.** Stages 1–6 implemented and oracle-pinned; the R2 Playwright
cutover smoke already runs against the Rust server.
**Remaining gap.** docker/compose + deployment docs; graceful-shutdown
decision; SV7 probe decision (O-S3); release-build differential run; sign-off;
retirement decision.
**Scope.** Ops/deployment artifacts and docs; optionally signal handling and a
header-only SV7 probe.
**Proof.** `docs/server-cutover-checklist.md` completed; oracle suites green on
the release build; deployment-host smoke.
**Legacy after.** C server removed from deployment; differential oracle
optionally retained.
**Risk.** Low; the code is already authoritative.

## 14. Part XIII — Explicit non-migration list

These should **remain** (do not equate "legacy" with "delete"):

1. **`musicpack-musepack-encoder` and `musicpack-mpc-tools`** — the deliberate
   LGPL-2.1-or-later isolation boundary and its frozen corpus. The *sidecar* is
   retired; the crates are the long-term implementation.
2. **Committed compatibility corpora and golden data** — `tests/data/*_c_reference.txt`,
   the `.jsonl` oracles, the encoder manifest/corpus, `cut_compat` fixtures.
3. **The C-created `library-c-reference.db` and C/Rust cross-verification
   tests** — DB-format permanence.
4. **Reference package/container/audio fixtures** — `.mpack` fixtures, `.mpak`
   packs, `.mpc` streams.
5. **The frozen Emscripten decoder's provenance** — keep the artifact and its
   `PROVENANCE-legacy-decoder.md` at least as an oracle after R4.4.
6. **The legacy repository** — immutable oracle; never modified.
7. **`web/player-core`** — the web orchestrator until an explicit, evidence-gated
   single-implementation decision (ADR 0003).
8. **The live-C differential suites** — transitional per ADR 0007, but kept
   until the retirement decision, not deleted pre-emptively.
9. **The `claxon` and bundled-SQLite dependencies** — scoped, documented
   exceptions; not "legacy C to remove".

## 15. Part XIV — R4 definition of done

> MusicPack has completed the legacy runtime migration when **no modern runtime
> path spawns a legacy binary or loads a legacy decoder artifact**, and the
> compatibility contracts are still pinned by retained oracles.**

Evidence-based criteria:

1. **Server runtime independence** — no subprocess/FFI; all endpoints auth'd and
   oracle-pinned; opens C v10 and Rust v11 databases; deployment artifacts
   exist; graceful-shutdown and SV7 decisions recorded; server retirement
   decision signed off. *(Largely met; closure is ops + decisions.)*
2. **Author runtime independence** — the app builds/validates/encodes/waveforms/
   packs/identifies with no bundled C binary; the bundled sidecars are gone and
   the encoder is the Rust crate; produced packages are byte/semantically
   equivalent to the frozen C oracle.
3. **Package writer authority** — the Rust core (or an app crate over it) writes
   canonical `.mpack` directories and `.mpak` containers; the C writer is
   oracle-only.
4. **Player runtime independence** — every runtime source (network and offline)
   decodes through Rust/WASM (or native browser for browser-native codecs); no
   frozen decoder on a user path.
5. **Codec runtime dependencies** — the Rust encoder is integrated; no C
   encoder in the runtime; decoding is Rust.
6. **Database / package / API / offline compatibility** — all still pinned by
   the retained oracle suites; no contract weakened.
7. **Behavioral regression coverage** — the permanent corpora and differential
   suites remain green.
8. **Declared permanent boundaries** — the LGPL encoder/tools crates, the
   scoped `claxon`/SQLite dependencies, and (if decided) the sonic analyzer are
   documented as intentional, not debt.
9. **No legacy-repository modification** at any point.

Deletion of compatibility/oracle infrastructure is explicitly **not** required.

## 16. Part XV — Recommended sequence

Derived from actual dependencies:

1. **R4.1** (core directory builder + identity promotion) — prerequisite for
   R4.2. Nothing else depends on it.
2. **R4.2** (Rust authoring pipeline) — depends on R4.1 and on the already-
   complete encoder crate. MusicBrainz matching is the long pole; a degraded
   first cut (exact-ID only, then matching) is possible because the host already
   fetches MB data.
3. **R4.3** (Author cutover) — depends on R4.2; retires the sidecars and decides
   the sonic boundary. Cannot precede R4.2.
4. **R4.4** (web offline Rust playback) — **independent** of R4.1–R4.3; can run
   in parallel. Requires only the browser source adapter.
5. **R4.5** (server cutover closure) — **independent**; mostly ops/docs and two
   small decisions; can run in parallel with any of the above.

Within R4.2, the natural order is `validate/verify` → `build` (needs R4.1) →
`encode` (needs the encoder) → `waveform` → `pack` → `identify`, because
`build` is the gate for every produce-artifact command and `identify` is the
only capability without a Rust equivalent.

Documentation-drift cleanup (stale `rust-*.spec.ts` headers, `author/README`
missing-script references, test-only web Rust artifacts, the already-skipping
node harness) rides along with whichever slice touches those files; it is a
cleanup, not a slice.

R5 (native) remains gated behind R1–R3 as recorded in ADR 0006 and does not
interact with R4.
